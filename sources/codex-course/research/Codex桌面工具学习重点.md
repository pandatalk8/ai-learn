# Codex 桌面工具学习重点

学习 Codex 桌面工具，最重要的不是把所有菜单和功能学一遍，而是掌握这条主线：

> 选对项目 → 建立任务 → 提供上下文 → 让 Codex 执行 → 审查改动 → 验证结果 → 沉淀工作流

## 一、必须优先掌握的 6 项能力

### 1. 项目和工作目录

首先要理解 Codex 在哪个目录中工作。

重点学习：

- 打开本地项目文件夹
- 确认当前工作目录
- 理解 Codex 可以访问哪些文件
- 区分普通聊天、Codex 任务和项目
- 一个任务对应一个明确的项目目录

工作目录错误，会导致 Codex：

- 找不到代码
- 修改错项目
- 使用错误的依赖和测试命令
- 无法理解完整项目结构

桌面端适合直接连接本地文件夹，并围绕本地项目组织任务。

参考：[Codex 桌面端快速开始](https://learn.chatgpt.com/docs/quickstart)

### 2. 任务和对话管理

Codex 桌面端的核心单位不是“聊天消息”，而是一个有明确结果的任务。

建议遵循：

- 一个任务只解决一个相对完整的问题
- 同一个问题继续使用原任务
- 出现不同实现方向时再 fork
- 已完成的任务及时归档
- 重要任务可以固定
- 不要在一个任务里完成整个项目的所有工作

例如可以分别建立：

- “分析登录模块结构”
- “修复登录重复提交”
- “为登录模块补充测试”
- “审查本次登录功能修改”

官方建议使用项目保存共享文件和说明，同时让每个任务围绕一个连贯的结果展开。

参考：[Projects and chats](https://learn.chatgpt.com/docs/projects)

### 3. 高质量任务描述

桌面工具再强，也需要明确任务。一个可靠的任务描述最好包含四项：

```markdown
目标：
修复用户连续点击登录按钮产生重复请求的问题。

上下文：
登录页面位于 src/pages/login。
相关接口封装位于 src/api/auth.ts。

约束：
不修改后端接口，不引入新的生产依赖。

完成标准：
提交过程中按钮不可重复点击；
请求失败后按钮恢复；
相关测试、类型检查和构建通过。
```

最重要的四个要素是：

- **Goal**：目标
- **Context**：上下文
- **Constraints**：约束
- **Done when**：完成标准

复杂、模糊或影响范围较大的任务，先使用 Plan 模式，让 Codex 调查代码、提出问题并制定计划，再开始修改。

参考：[Codex 最佳实践](https://learn.chatgpt.com/guides/best-practices)

### 4. 终端、测试和验证

这是桌面端最重要的工程能力之一。

需要学会让 Codex：

- 运行项目
- 查看错误日志
- 运行单元测试
- 运行 lint
- 运行类型检查
- 执行构建
- 根据失败结果继续修复

不要只说：

> 修改完成了吗？

应该要求：

> 运行相关测试、类型检查和构建；如果失败，分析原因并继续修复。最后说明运行了哪些验证，以及哪些内容没有验证。

判断 Codex 是否完成任务，主要看证据，而不是看它是否生成了代码。

### 5. Diff 审查与反馈

Codex 修改完成后，要学会使用桌面端的 Diff 面板：

- 查看新增、删除和修改内容
- 判断是否修改了无关文件
- 点击具体代码行提供反馈
- 要求 Codex 解释关键改动
- 要求它对自己的修改做一次 review
- 必要时使用 `/review`

重点检查：

- 是否满足原始需求
- 是否产生行为回归
- 是否出现过度设计
- 是否引入不必要的依赖
- 是否漏掉异常和边界情况
- 测试是否真正覆盖了修改

Diff 审查是“人负责判断、Codex 负责执行”的关键交界面。

参考：[Codex Code Review](https://learn.chatgpt.com/docs/code-review?surface=app)

### 6. Git 和 Worktree

当你和 Codex 同时工作，或者同时运行多个任务时，要重点学习 Worktree。

Worktree 可以让每个任务使用独立工作目录和 Git 分支，避免：

- 多个任务同时修改相同文件
- Codex 覆盖你正在编写的代码
- 一个实验性任务污染主工作区
- 后台任务直接修改当前代码

适合使用 Worktree 的场景：

- 同时执行多个开发任务
- 尝试不同实现方案
- 后台运行较长任务
- 自动化任务可能修改代码
- 当前工作区存在未完成修改

如果任务只做分析、不修改代码，一般不需要创建 Worktree。

参考：[Git Worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees)

## 二、第二阶段应该学习的能力

### 7. `AGENTS.md`

`AGENTS.md` 是提供给 Codex 的项目说明书，适合记录长期有效的信息：

```markdown
# 项目说明

## 技术栈

- Next.js
- TypeScript
- PostgreSQL

## 常用命令

- 开发：pnpm dev
- 测试：pnpm test
- 类型检查：pnpm typecheck
- 构建：pnpm build

## 修改规则

- 不直接修改数据库生产数据
- 不引入新的状态管理框架
- 修改 API 时必须更新相关测试

## 完成标准

- 测试通过
- 类型检查通过
- 构建通过
- 总结修改文件和剩余风险
```

适合写入 `AGENTS.md` 的内容：

- 项目结构
- 启动和测试命令
- 编码规范
- 架构约束
- 禁止事项
- 完成标准

不要把一次性需求写进 `AGENTS.md`。一次性需求放在当前任务中，长期规则才放进去。

参考：[AGENTS.md 官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

### 8. 权限和沙箱

要理解 Codex 能做什么，以及什么操作需要确认：

- 只读访问
- 工作区写入
- 完整文件访问
- 网络访问
- 外部应用操作
- 危险命令
- 自动化任务的无人值守权限

建议初学阶段使用默认或较严格权限。只有在明确了解任务行为，并且信任当前项目时，才逐步放宽。

特别注意：

- 删除文件
- 数据库迁移
- 安装生产依赖
- 发布和部署
- 推送 Git
- 操作外部账号
- 修改项目外部文件

### 9. 浏览器和 Computer Use

Web 项目不能只验证“能构建”，还要验证“真正能使用”。

需要学习：

- 启动本地开发服务器
- 使用内置浏览器打开页面
- 检查视觉效果
- 点击完整用户流程
- 检查表单、跳转和错误状态
- 截图并与需求对比
- 根据浏览器控制台错误继续修复

这可以形成完整闭环：

```text
修改代码 → 启动应用 → 浏览器操作 → 发现问题 → 修复 → 再次验证
```

## 三、最后再学习的高级能力

### 10. Skills

如果你经常重复同一套流程，例如：

- PR 审查
- 发布检查
- 日志分析
- 故障排查
- 文章生成
- 数据分析

可以把它封装成 Skill。

Skill 解决的是：

> 每次都要重复解释“应该如何完成这类任务”的问题。

### 11. Plugins、MCP 和连接器

当 Codex 需要访问项目外部的信息时，再学习：

- GitHub
- Slack
- Notion
- Google Drive
- Linear
- 数据库
- 部署平台

不要一开始安装所有插件。先确定一个真实工作流，再连接一个真正需要的系统。

### 12. 自动化任务

工作流已经能够稳定手动运行后，才适合自动化，例如：

- 每天汇总代码改动
- 定期检查 CI
- 扫描潜在问题
- 生成发布说明
- 跟踪 PR 状态
- 定期生成项目报告

自动化前必须先确保：

- 提示词稳定
- 权限足够但不过度
- 输出容易审查
- 失败时不会产生破坏
- 修改代码时使用独立 Worktree

官方也建议先手动测试工作流，再创建计划任务。

参考：[Scheduled tasks](https://learn.chatgpt.com/docs/automations)

## 推荐学习顺序

```text
本地项目
  ↓
任务与对话
  ↓
任务描述与 Plan 模式
  ↓
终端、测试和构建
  ↓
Diff 与代码审查
  ↓
Git Worktree
  ↓
AGENTS.md
  ↓
浏览器验证
  ↓
Skills 和插件
  ↓
自动化与多任务协作
```

## 核心总结

如果只选最重要的四项，就是：

1. 正确选择项目和工作目录
2. 写清楚目标、上下文、约束和完成标准
3. 使用测试、构建和浏览器验证结果
4. 使用 Diff 和 Worktree 安全管理代码修改

真正掌握这四项，基本就掌握了 Codex 桌面工具大部分核心生产力。
